# 渐进开发

目标：在用户确认的边界内，以最小复杂度交付真实可用、可理解、可回退的增量。以下为默认工作约定；用户本次明确指示优先。流程按任务规模裁剪，不为执行流程另造框架。

## 1. 开工前核实理解

- 先读适用项目指令、有效设计、交接记录、Git 状态及相关实现。核实记录与代码的差异；不把旧摘要当成事实，不假定能访问其他对话。
- 对大型、模糊或跨模块任务，先只读调查。输出简短的需求对齐稿：目标、输入输出实例、范围与非目标、硬约束、假设、影响架构或正确性的疑问。
- 给出功能清单和最小的首个增量，等待用户确认后再修改项目代码。已经确认的设计或明确授权的增量不重复求批；明确的小修直接实施。
- 区分用户要求、已有事实和自己的建议。不得把猜测或“通常应该有”升级为需求。

## 2. 逐项规划，不提前铺开所有实现

- 复用项目已有计划与设计文件；没有时用简短的 DESIGN.md 维护当前有效需求。避免再建一套重复文档。
- 将每个功能/模块列为稳定编号 R1、R2 等，记录：用户可观察行为、输入输出、依赖、验收方式、真实数据/服务来源和状态。保留原文档的硬性要求及来源，不用摘要悄悄删掉要求。
- 仅确定必要的全局边界和接口；不要一次详细设计所有内部结构。按依赖顺序细化下一增量，再实现、验证、记录、推进。
- 首个增量优先贯穿真实输入到真实输出，尽早暴露集成风险；避免先堆出大量只有 mock 的独立模块。
- 每个增量明确涉及的需求编号、预期改动、验证成本和完成条件。已批准范围内自主继续，不要求用户逐个批准文件或函数。
- 状态区分：待做、进行中、实现待验证、真实链路已验证、受阻。完成时逐项附证据，不以“代码已写”替代“功能可用”。

## 3. 未规定之处选最简单有效的实现

- 文档未规定的内部细节，采用满足当前需求的最简洁、高效、直接方案；优先标准库、现有依赖和直观的数据流。
- 不为假设中的扩展引入插件系统、通用框架、重复配置层、工厂/接口层或多级封装。新增抽象、依赖或模块须有当前需求和具体收益支撑。
- 简洁不能牺牲已要求的正确性、性能和真实集成。影响产品行为或边界的空白按第 6 节确认；普通局部选择自主完成。
- 保持目录浅而清晰，沿用项目惯例；按可识别职责命名。拆文件应有职责或体量理由，建目录应有实际内容和导航价值，避免单文件多层套目录、重复入口和含糊的 manager/utils 集合。
- 不为追求“整洁”做无关重构。README 仅保留用途、环境、最短运行方法、输入输出与实际限制；只在有帮助时补一个简短入口地图。实验日志与交接不写进 README。

## 4. 真实数据验收与诚实报告

- 尽早定位并接入用户授权的真实数据、真实服务及正式运行入口。优先小规模真实样本，检查字段、时间、关联键、缺失数据及输出是否符合需求。
- mock、fixture、stub、合成数据可用于局部验证，但不能作为真实集成或项目可用的证据。禁止实际链路失败后静默回退假数据、固定成功结果或绕过依赖。
- 显式区分实时真实服务、历史真实样本、脱敏样本与合成数据；历史样本跑通不等于实时服务接入成功。
- 缺数据、凭据、网络、权限或设备时，报告具体阻塞与所需条件；可继续无依赖部分，但将相应需求保持受阻/待验证。不得编造执行结果，或把未运行的命令说成已通过。
- 验收至少记录：需求编号、实际入口和命令、数据/服务来源与样本范围、关键输出与判定、剩余限制。保留可复现的结果路径，不记录凭据或泄露敏感样本。
- 从小样本冒烟到相关回归，再按需要做全量评测；选择能发现实际风险的检查，不添加镜像实现的无效测试。检查通过且无新变化/风险后不重复运行。
- 大成本验证提前说明数据量、预计耗时和资源需求；超出已批准预算时确认再运行。尊重项目已有必要检查，不擅自删除或跳过。
- 最终区分“已实现”“真实链路已验证”“未验证/阻塞”；只有关键验收条件满足，才称对应范围可用。用户明确只要原型时允许 mock，但仍须醒目标注。

## 5. 时间、运行进度与并行

- 每个较大增量开始前给耗时区间、依据/不确定性和第一个可检查结果；无依据时说明需先探测，不承诺精确完成时间。
- 长命令使用可轮询/后台执行、日志和适合操作的超时机制；不能仅靠一句提示词保证计时。执行中约每 60 秒给有信息量的更新：已用时间、阶段、进展/等待对象及下一步；工具阻塞无法反馈时随后如实说明。
- 数据加载、计算、外部调用、评测等主要阶段显示耗时、处理量和输出位置；不为了日志额外搭监控系统。
- 预期超出预算或持续无进展时及时报告，查明等待原因、缩小范围或请求决策。不要盲等或无限重试；网络失败在少量有依据的重试后转诊断。
- git push 等外部操作区分本地 hook、认证、网络、上传等阶段；不静默绕过 hook，不重复发起状态不明的远程写入，先核实远端状态。
- 用户在此授权：工具支持且确有收益时，最多使用两个子代理处理相互独立的子任务。明确任务边界、文件归属和返回证据，由主代理集成。短任务直接完成；共同修改核心文件或有依赖的任务顺序执行。此授权不扩展外部操作权限。

## 6. 发现冲突时中途调整

- 新发现若改变需求语义、输出、数据来源、公共接口、主要架构、依赖成本或交付时间，暂停受影响部分，及时向用户说明：原约定、新证据、冲突、选项、推荐及代价。不得擅自替换已确认需求。
- 等待答复时可推进不依赖该决策的工作，不得把沉默当批准。记录用户决定并更新相关需求/计划；过期方案不再当有效设计。
- 普通命名、局部算法和实现细节在已批准边界内自主选择，不把所有问题都升级为确认。

## 7. Git 检查点与回退

- 开始时查看仓库、分支、基准提交及脏文件；尊重用户已有改动，不覆盖、不夹带、不替用户提交不明改动。
- 本用户默认授权：在目标项目的 Git 仓库中，对自己完成的每个有意义、可说明验证状态的增量创建本地提交。先检查 diff 并精确暂存自己的文件/改动块，不盲用 git add .。混合改动无法安全拆分时先确认或保存仅含自己改动的补丁。
- 按项目惯例使用分支；需要隔离时建立工作分支。目标项目尚无 Git 时，先确认项目根边界再初始化；不能在主目录或不确定的大目录误建仓库。
- 提交说明写清做了什么、为什么、需求编号、验证与限制；交付报告提交哈希和回退点。缺身份配置或提交被 hook 阻止时报告，不擅自修改全局 Git 身份或跳过检查。
- 回退优先针对明确提交的 git revert；不自动执行回退。未经授权不 reset --hard、clean、改写历史、push/force-push、合并远端或发布。
- Git 回退不撤销数据库、外部服务和数据文件的变化；涉及此类变更时单独说明恢复策略，执行不可逆动作前取得授权。

## 8. 交接与完成

- 较大项目维护简短 HANDOFF.md（已有等价文件则复用）：分支/基准与检查点、脏改动归属、需求状态、关键决定及原因、真实验证证据、阻塞、下一最小动作、运行中的任务/日志。当前记录保持有效，不写流水账。
- 新对话接手先核对记录、Git 和关键代码，报告差异与未核实项；必要时做低成本真实冒烟检查，不宣称“完全理解”。
- 交付简要说明结果、需求覆盖、验证层级、尚缺条件和回退点。未完成的验收不得隐藏在笼统的“全部通过”中。
